# P5 implementation and acceptance

P5 follows the formal beta roadmap's “URL Scheme and restore center”, not the original MVP's Phase 5 local release. Scope: macOS 14+, WeChat 4.x, ordinary files, image high layers and video Raw layers. Never modify WeChat databases or replace normal viewing/playback layers.

Status (2026-09-08): **P5 complete within the agreed isolated-sample scope.** Native Microsoft Excel invocation closes the final Office acceptance item; the real test-account login round trip was confirmed on September 7. WPS direct-link compatibility remains limited as documented below. Real WeChat and distribution acceptance remain P6/P7 work.

## Behavior

- The menu bar, status center and archived-file detail open one reusable restore window. Links select an archive without initiating a transfer or changing the current scan root.
- `RestoreLink` validates the existing `binding-` plus 32/64 lowercase hex identifiers. The sole allowed query is the exact `OR=PowerPoint` tag, which native PowerPoint appends when invoking a custom scheme; every other query, duplicate, encoding variant and fragment is rejected. Binding lookup uses the encrypted manifest's keyed token index. Lists are paged in groups of 50, independent of scans and local source presence.
- Ordinary files default to `~/Downloads/WeChat Archive Restores/`. Media default to controlled original-path restoration; every type also supports Downloads and a selected directory. Writing to WeChat requires a visible confirmation and never requires terminating WeChat.
- Matching existing originals are accepted after verification. Other existing files must be manifest-matched, unchanged tombstones. Downloads first go to a temporary file, with size/SHA checks before committing. Original-path tombstones are atomically exchanged and the displaced file is checked before removal. Empty targets use an exclusive rename. Symlink/non-file targets are rejected.
- Image restores require the ordinary viewing layer. Video restores also require playback and a cover/thumbnail. Checks run before download and again before committing.
- A download copy does not change the original-path local state or remove quarantine/tombstone metadata. Failed and interrupted restore attempts can retry. Old `RESTORE_FAILED` local states are reconciled using the actual original, placeholder and quarantine.
- All app windows share operation state; restore and manual release/rollback/finalize cannot run simultaneously. Opening another link does not change an in-flight restore's target.
- PDF, DOCX, PPTX and XLSX tombstones contain explicit hyperlink annotations/relationships, metadata and visible recovery IDs. Text and ZIP instructions retain a copyable URL. Existing tombstones are not rewritten.

## Development app and smoke tests

Build with `Scripts/build-app.sh [debug|release]`. The result is `.build/app/WeVault.app` with a development-only ad-hoc signature. This is not a signed/notarized beta distribution. `swift run WeVault` remains available for ordinary development, but does not install a URL Scheme handler.

For **synthetic desktop acceptance**, first close any previous copy of the packaged development app, then:

```sh
Scripts/build-app.sh debug
WEVAULT_P5_TEST_DIRECTORY="$PWD/.build/p5-smoke" \
WEVAULT_P5_ARTIFACT_DIR="$PWD/.build/p5-artifacts" \
swift test --filter RestoreCenterTests
open --env "WEVAULT_P5_TEST_DIRECTORY=$PWD/.build/p5-smoke" \
  -a "$PWD/.build/app/WeVault.app"
```

The debug-only environment flag uses synthetic manifest storage and a deliberately fixed **test-only** key; it does not load production account Keychain items and disables automation/scan-root persistence. Login/configuration is blocked by default. To check a real test-account login round trip, additionally launch with `WEVAULT_P5_INTERACTIVE_AUTH=1`: authentication contacts the existing API, but account sessions and STS configuration remain in memory only and disappear on exit. Never put real user data in this fixture directory. Release builds ignore these flags. Optional `last-incoming-url.txt` in synthetic storage records only links delivered during this explicit debug mode.

Use `.build/p5-artifacts/placeholder.pdf`, `.docx`, `.pptx` and `.xlsx` to check native file behavior and read their exact fixture IDs. Open their links with the packaged fixture app already running. The generated fixture records intentionally have no real cloud data, so full successful transfers are covered by mock-backed service tests instead of live credentials.

### Acceptance checklist

- Cold launch with a link, warm launch, repeat a link, change targets, close/reopen the restore window.
- Confirm the record remains selected when opening/closing cloud settings; real account/STS operations retain existing P2 authorization checks.
- Unknown IDs, invalid links, unavailable keys and corrupt manifests must show explicit errors rather than an empty-success state.
- Confirm a source missing from the current scan still resolves, original-path confirmation includes the filename, and download recovery does not mark that source restored.
- Open PDF/Office samples without repair prompts, read the strong placeholder warning, then invoke the actual hyperlink. Office may show its normal external-link confirmation; a file-repair warning is a failure.
- Run `swift test`, `swift build`, `npm --prefix server test` and `npm --prefix server run build`.

## Deferred work

The P4 gaps recorded at the P5 handoff have now been implemented in the follow-up [P4 work](P4.md): bounded scanning/hashing, scheduled isolation and quarantine finalization. P5 itself did not expand into that work.

P6 owns real WeChat click/export/playback acceptance and additional sample coverage. P7 owns distribution signing, notarization, updates and broader resource optimization. Backend object lookup cannot reconstruct lost local path/binding metadata; missing-manifest errors must not promise automatic original-path recovery. P5 adds no backend API or cloud migration.
